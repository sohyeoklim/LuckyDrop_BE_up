# LuckyDrop API 자동화 실습

## 1. 실행

테스트 전용 Docker 서비스와 `api-test` 프로필 서버가 실행 중이어야 합니다.
API는 localhost:18080, DB는 localhost:13306/luckydrop_api_test를 사용합니다.
메일 및 Google 로그인은 이번 테스트에 포함하지 않습니다.

```powershell
cd C:\LuckyDrop_B\api-tests
npm.cmd ci
npm.cmd test
npm.cmd run report
```

API 요청만 사용하므로 브라우저 바이너리 설치는 필요하지 않습니다.
`npm.cmd ci`는 최초 설치 또는 package-lock.json 변경 시 실행합니다.

## 2. 첫 케이스: 정상 응모

| 단계 | 내용 |
| --- | --- |
| 준비 | 새 일반 사용자와 호스트, 티켓 10장, 비용 2장인 진행 중 드로우 |
| 조건 | 첫 응모·당일 응모 보상을 이미 수령한 상태로 설정 |
| 로그인 | 실제 로그인 API 호출, 응답 쿠키를 다음 요청에 사용 |
| 사전 확인 | 잔액 10장, 응모 내역 0건 |
| 실행 | 새 Idempotency-Key와 count: 3으로 응모 |
| 검증 | 응답 200, 차감 6장, 잔액 4장, 응모 3회, USE 원장 -6 한 건 |

`tests/entry.spec.js`가 실제 검증 코드입니다.
`helpers/seed.js`는 DB에 사전 조건을 만드는 fixture입니다.
fixture는 회원가입이나 미션 보상 기능의 검증이 아닙니다.
미션 기록은 보상 간섭을 제거하기 위해 합성한 상태이며, 보상 지급 검증은 별도 케이스로 추가합니다.

매 실행마다 새 사용자와 드로우를 생성하므로 이전 실행의 잔액에 의존하지 않습니다.
실행 후 데이터는 테스트 DB에 남습니다. 실패 시에도 남겨서 조사할 수 있습니다.
기존 개발 DB를 초기화하거나 삭제하지 않습니다.
날짜 기준은 Asia/Seoul입니다. 서버도 같은 시간대로 실행해야 하며,
자정을 가로지르는 실행은 일일 미션 보상 조건이 달라질 수 있습니다.
CI는 `.github/workflows/api-tests.yml`에 구성되어 있습니다.

## 3. 직접 해볼 실습

1. `npm.cmd test -- --grep "정상 응모"`를 실행해서 `1 passed`를 확인합니다.
2. 마지막 잔액 검증의 `toBe(4)`만 `toBe(5)`로 바꾸고 실행합니다.
3. `Expected: 5`, `Received: 4`로 실패하는지 확인합니다.
4. 다시 `toBe(4)`로 복구한 뒤 통과를 확인합니다.

이 실습은 테스트가 실제 잘못된 예상값을 감지하는지 확인하는 연습입니다.
코드를 커밋하기 전에는 올바른 예상값으로 복구합니다.

## 4. 두 번째 케이스: 티켓 부족

티켓 10장으로 비용 2장인 드로우에 6회(12장) 응모합니다.
HTTP 400과 `티켓이 부족합니다.` 메시지를 확인하고,
요청 전후의 잔액·응모 내역·티켓 원장을 비교해 변경이 없음을 검증합니다.
오류 응답만 확인하면 잘못된 차감이나 일부 저장을 놓칠 수 있기 때문입니다.

```powershell
# 전체 케이스 실행
npm.cmd test
# 티켓 부족 케이스만 실행
npm.cmd test -- --grep "티켓 부족"
```

## 5. 세 번째 케이스: 같은 요청 재전송

동일한 드로우에 `count: 3`과 같은 `Idempotency-Key`로 순차적으로 두 번 요청합니다.
첫 요청은 200, 두 번째 요청은 현재 계약에 따라 400과 `이미 처리된 요청입니다.`를 반환해야 합니다.
첫 요청 이후 상태와 두 번째 요청 이후 상태를 비교해 잔액 4장, 응모 3회,
사용 원장 -6 한 건이 그대로 유지되는지 검증합니다.

키는 요청마다 생성하지 않고 한 번 생성한 값을 재사용해야 합니다.
두 번째 응답에서 상태 코드뿐 아니라 오류 메시지도 확인합니다.
남은 잔액이 4장이므로, 메시지를 확인하지 않으면 티켓 부족으로 인한 400을
중복 방지 성공으로 오해할 수 있기 때문입니다.
이 케이스는 순차 재전송 검증이며 동시 요청에 대한 경쟁 조건 검증은 포함하지 않습니다.

```powershell
# 중복 요청 케이스만 실행
npm.cmd test -- --grep "중복 요청"
# 전체 실행: 3 passed 예상
npm.cmd test
```

## 6. 다음 단계

GitHub에 push하거나 PR을 생성하면 `API regression tests`가 실행됩니다.
Java 21, Node.js 24, MySQL, Redis를 준비하고 실행 JAR을 빌드합니다.
`api-test` 프로필로 서버를 시작하고 HTTP 응답을 확인한 뒤 테스트 3개를 실행합니다.
서버와 DB 시간대는 Asia/Seoul로 맞춥니다.
이 workflow는 API 테스트를 실행하며 Gradle의 별도 JUnit 테스트 실행은 포함하지 않습니다.

GitHub 저장소 → Actions → API regression tests → 실행 항목에서 단계별 로그를 확인합니다.
실패하면 `Run API regression tests`에서 Expected/Received를 확인하고,
하단 Artifacts의 `api-test-results-...`를 다운로드해 HTML 리포트와 서버 로그를 확인합니다.
리포트와 로그는 성공/실패 모두 7일간 보관합니다.
각 실행에서 새 DB를 생성하며 실제 서비스 비밀값이나 GitHub Secrets는 필요하지 않습니다.
테스트 전용 계정과 고정 비밀번호는 로컬/CI 전용입니다.

다음 테스트 확장 대상은 종료 드로우, 미인증 요청, 동시 요청입니다.
